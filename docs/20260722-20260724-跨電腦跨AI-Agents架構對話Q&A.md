# 跨電腦、跨 AI Agents 架構白話 Q&A

> 本筆記依 2026-07-22 至 2026-07-24 的討論順序整理。目的不是教 Git 指令，而是說明：ChatGPT、Codex、Claude、Antigravity、OpenCode 在不同時間接手同一專案時，如何避免讀到舊規則、舊程式或舊 `HANDOFF.md`。

## 一句話結論

**專案只在本機 NTFS 工作；GitHub 保存正式版本；Google Drive 發布全域規則與同步知識；Obsidian保存給人閱讀的學習及專案紀錄。每次修改前先「開工」，結束後一定「收工」。**

---

## 一、先看懂介面與基本名詞

### Q1：Codex 左上角的 `my-agent-2026 main` 代表什麼？

**A：**

- `my-agent-2026`：目前開啟的 Git 專案或 repository 名稱。
- `main`：目前所在的 Git branch，也就是主要分支。

它的意思是：「目前正在 `my-agent-2026` 專案的 `main` 分支工作」，不是 Agent 名稱，也不是 AI 模型版本。

畫面上的 `+8,666 -137` 通常表示目前相對 Git 基準新增與刪除的程式行數；`Create PR` 是把目前分支提出 Pull Request。

## 二、為什麼不能直接把 Google Drive 當專案工作區

### Q4：Google Drive 當主要工作位置與 SSOT，再讓不同 Agent 從這裡同步，可行嗎？

**A：可以存放資料，但不適合直接當多 Agent 的程式執行工作區。**

Google Drive 擅長檔案同步，Git 擅長版本順序、衝突處理與變更追蹤。若不同電腦或 Agent 直接在 Drive 中修改同一專案，可能遇到：

- Drive 尚未同步完成，Agent 讀到舊檔。
- 兩台電腦同時改檔，產生衝突副本。
- `.git`、大量小檔、套件目錄或暫存檔同步不完整。
- Agent 無法判斷哪一份才是正式最新版。
- Obsidian、Drive、Git 各自出現一份看似最新的內容。

因此新的設計是：**Google Drive 不再是程式執行區；正式專案在本機 NTFS，正式版本在 GitHub。**

### Q5：`G:\我的雲端硬碟\2026Claude\core_rule.md` 還可以作為 SSOT 嗎？

**A：可以，但它是「全域規則內容的唯一母檔」，不是專案程式碼的 SSOT。**

權責要分清楚：

- `core_rule.md`：全域 AI 工作規則的母檔。
- GitHub project repo：專案程式、文件與 `HANDOFF.md` 的正式版本。
- `AGENTS.md` / `CLAUDE.md`：由母檔產生或同步出的 Agent 可讀版本。
- Obsidian：人類閱讀的知識與歷史紀錄。

只允許修改 `core_rule.md` 母檔，再產生其他規則檔，才不會有三份規則各自被修改。

### Q6：Google Drive 的 `core_rule.md` 仍可能因網路中斷或 Drive 未啟動而沒更新嗎？

**A：是，這是 Google Drive 層仍存在的同步風險。**

但新架構不是讓 Agent 毫無檢查地直接使用 Drive 內容，而是：

1. `project-startup` 檢查規則版本與雜湊。
2. `sync-health` 比對 `core_rule.md`、Skills、manifest 與 Agent adapters。
3. 發現不一致就阻擋開工，不准繼續修改。

因此，Drive 延遲可能發生，但應該被檢查機制攔下，不應默默形成分岔。

### Q7：Obsidian 由 Google Drive 還是 GitHub 同步？

**A：Obsidian vault 由 Google Drive 同步；它不負責同步程式正式版本。**

Obsidian 的用途是：

- 專案摘要
- 收工紀錄
- 學習筆記
- 決策脈絡
- 方便搜尋與連結知識

專案正式內容仍由 Git/GitHub 管理。不要把 Obsidian 筆記反向當成程式最新版來源。

## 三、四層架構如何分工

### Q8：新的防分岔架構有哪四層？

**A：**

| 層級 | 定位 | 可以做什麼 | 不應做什麼 |
|---|---|---|---|
| 本機 NTFS | 唯一執行工作區 | 編輯、測試、建置、執行 Agent | 不靠 Drive 的即時同步決定最新版 |
| 本機 Git + GitHub | 正式版本與交接權威 | commit、push、版本、回復、比對 remote HEAD | 不保存密碼或未篩選的個人狀態 |
| Google Drive | 全域規則母檔與跨裝置知識同步 | 發布 `core_rule.md`、同步 Obsidian vault | 不直接執行正式專案 |
| Obsidian | 人類第二大腦 | 保存摘要、學習、決策與歷史紀錄 | 不當程式碼或 `HANDOFF.md` 的正式來源 |

其中 Git 與 GitHub 放在同一層理解：Git 是本機版本機制，GitHub 是遠端共同權威。

### Q9：哪些檔案會同步回 Google Drive？

**A：原則上只同步「規則發布與知識紀錄」，不把整個執行專案鏡像回 Drive。**

主要包括：

- `G:\我的雲端硬碟\2026Claude\core_rule.md`
- 需要發布到 Drive 的共用規則或 Skills 副本
- `G:\我的雲端硬碟\第二大腦` 中的 Obsidian 筆記
- 經明確定義的知識輸出、會議紀錄或人工閱讀資料

不應同步：

- 專案 `.git` 目錄
- `node_modules`、快取、build 暫存檔
- Agent session、token、登入資訊
- 用來執行的完整 active project 工作樹

### Q10：哪些內容要 commit + push 到 GitHub？

**A：會影響正式版本、下次接手或架構行為的檔案，都要進 GitHub。**

例如：

- 專案程式與正式文件
- `PROJECT.md`
- `HANDOFF.md`
- 專案層 `AGENTS.md`、`CLAUDE.md`
- 四個共用 Skills
- 同步與稽核腳本
- `architecture-manifest.json`
- 架構指南與 release tag

單純個人閱讀的 Obsidian 學習筆記，通常不需要提交到專案 GitHub。

## 四、四個 Skills 各自負責什麼

### Q11：`project-init-sync` 的定位是什麼？

**A：只用於「建立全新專案」。**

它會建立標準專案骨架，包括：

- `PROJECT.md`
- `HANDOFF.md`
- `AGENTS.md`
- `CLAUDE.md`
- 正確的本機 NTFS 路徑
- Git remote、branch 與版本根目錄資訊
- Obsidian 專案紀錄位置

它不是每天開工用的 Skill。

### Q12：`project-startup` 的定位是什麼？

**A：每次開始或接手既有專案前的唯讀安全閘門。**

它要確認：

- 現在位於本機 NTFS 正式工作區。
- Git root、branch、remote 正確。
- 本機 HEAD 與 GitHub remote 狀態可接續。
- `HANDOFF.md` 存在且 `handoff_ready: yes`。
- 全域規則、Skills 與架構版本一致。
- 沒有上一位 Agent 尚未完成的交接。

檢查通過前，Agent 不得修改專案。

### Q13：`project-wrapup` 的定位是什麼？

**A：每次工作結束時，把本次成果完整封存並交棒。**

強制流程包括：

1. 完成修改與測試。
2. 更新 `PROJECT.md`。
3. 更新 `HANDOFF.md`。
4. `HANDOFF.md` 必須包含 `handoff_ready`、開工 commit、branch、remote、驗證時間。
5. `HANDOFF.md` 必須納入本次 commit。
6. commit 並 push。
7. push 後確認 GitHub remote HEAD 等於 local HEAD。
8. 確認 GitHub 上的 `HANDOFF.md` 與本機雜湊相同。
9. 寫入 Obsidian 收工紀錄。

若 push 或驗證失敗，只能回報 `partial` 或 `blocked`，不能宣稱收工成功。

### Q14：`sync-health` 的定位是什麼？

**A：它是唯讀的架構健康檢查，不負責偷偷修檔。**

它會稽核：

- 本機 NTFS 路徑
- GitHub remote 狀態
- `core_rule.md`
- 四個 Skills
- 架構 manifest 與 hash
- Claude、Codex、Antigravity、OpenCode adapters
- chezmoi
- Windows 定期排程

目前 Windows 排程 `Claude-SyncHealth-Weekly` 已改為每週執行本機 NTFS 的新版完整稽核。

### Q15：為什麼要刪除舊的 `project-kickoff`？

**A：因為它與 `project-startup` 功能重疊，容易讓 Agent 不知道應使用哪一個入口。**

新規則是：

- 新專案：`project-init-sync`
- 既有專案開工或接手：`project-startup`
- 收工交棒：`project-wrapup`
- 定期健檢：`sync-health`

入口越單一，越不容易繞過檢查。

## 五、Agent 之間如何安全接手

### Q16：ChatGPT、Codex、Claude、Antigravity、OpenCode 可以都做同一專案嗎？

**A：可以，但必須「不同時間、依序接手」，不能同時修改。**

正確流程：

```text
前一個 Agent 開工檢查
        ↓
單一 Agent 在單一 branch 修改與測試
        ↓
收工：commit + push + HANDOFF
        ↓
確認 local HEAD = GitHub remote HEAD
        ↓
下一個 Agent 執行 project-startup
        ↓
讀取最新 commit、規則與 HANDOFF
        ↓
確認通過後才開始修改
```

這個設計可以輪流換 Agent，也可以換電腦；關鍵是任何時間只有一位實作者。

### Q17：`handoff_ready: no` 代表什麼？

**A：代表上一位 Agent 尚未完成可安全交接的狀態。**

可能原因包括：

- 還有未提交修改。
- push 失敗。
- remote HEAD 驗證失敗。
- 測試未完成。
- `HANDOFF.md` 沒有納入最新 commit。
- 規則或 Skills 健檢失敗。

下一位 Agent 看到 `handoff_ready: no` 時，禁止開始修改，只能先協助排除交接問題。

### Q18：每天每個做過的專案都執行「收工」，下次都先執行「開工」，就不會讀到舊資料嗎？

**A：理解基本正確，但有三個前提。**

1. 每次只允許一位 Agent 修改同一專案。
2. 收工必須真的 push 成功，而且 remote HEAD 驗證相同。
3. 開工檢查失敗時要停止，不能人工略過警告。

做到這三點，就能大幅降低讀到舊規則、舊程式或舊 `HANDOFF.md` 的風險。這不是保證網路永遠不出錯，而是讓錯誤被看見並阻擋。

### Q19：是否需要定期 check？

**A：需要。開工與收工是逐次檢查；每週 `sync-health` 是整體稽核。**

三層檢查節奏：

- 每次修改前：`project-startup`
- 每次工作結束：`project-wrapup`
- 每週固定：`Claude-SyncHealth-Weekly`

若更動 `core_rule.md`、Skills、manifest 或 Agent adapters，應立即額外執行一次完整 `sync-health`，不必等到每週排程。

## 六、HEAD、remote 與雜湊的白話解釋

### Q20：`local HEAD = GitHub remote HEAD` 代表什麼？

**A：代表本機目前最新 commit，與 GitHub 該 branch 的最新 commit 是同一個。**

白話說就是：

> 這台電腦已經把目前正式版本完整推到 GitHub，GitHub 沒有少一個 commit，本機也沒有落後 GitHub。

它只證明 Git commit 對齊，不代表：

- 沒有尚未 commit 的檔案。
- Google Drive 已同步。
- Obsidian 已同步。
- 未來不會有人再 push 新 commit。

所以還要搭配 clean working tree、`HANDOFF.md` 與 `sync-health` 一起判斷。

### Q21：確認 remote HEAD 的目的為何？

**A：確認「正式交棒點」真的已經存在 GitHub，而不是只存在上一位 Agent 的電腦。**

如果只 commit 沒 push：

- 本機看起來完成。
- 下一台電腦卻抓不到。
- 下一位 Agent 會從舊版繼續做。
- 兩邊最後可能形成不同歷史。

因此 remote HEAD 驗證是收工能否宣告成功的必要條件。

### Q22：「HANDOFF 檔案雜湊完全相同」中的雜湊是什麼？

**A：雜湊可以理解成檔案內容的數位指紋。**

系統把檔案內容經過 SHA-256 計算，得到一串固定長度字元：

- 內容完全相同，雜湊就相同。
- 即使只改一個字，雜湊通常也會完全不同。

因此，本機與 GitHub 上的 `HANDOFF.md` 雜湊相同，可證明兩邊檔案內容一致。但它只證明「相同」，不保證內容本身一定正確，所以仍要檢查欄位與狀態。

### Q23：GitHub 與 HANDOFF 都確認沒有分岔，下一個 Agent 就不會讀到舊資料嗎？

**A：在它確實執行 `project-startup`，而且檢查通過的前提下，這個理解正確。**

完整判斷需要同時成立：

- pull/fetch 後的 Git commit 是最新 remote HEAD。
- `HANDOFF.md` 是該 commit 內的版本。
- `handoff_ready: yes`。
- 規則與 Skills hash 正確。
- Agent 沒有改去 G 槽舊工作區執行。

只看 GitHub 網頁，卻沒有在本機執行開工檢查，仍不能算完整防護。

## 七、Workspace 與 Claude 的正確使用方式

### Q24：後續專案 Workspace 應該在 C 槽還是 G 槽？

**A：正式 Workspace 一律在 C 槽本機 NTFS。**

正確路徑：

```text
C:\Users\user\Documents\Codex\2026Claude\100_Todo\projects\active
```

舊路徑：

```text
G:\我的雲端硬碟\2026Claude\100_Todo\projects\active
```

G 槽舊 active 路徑只能作為歷史資料或知識來源，不能再當 Agent 的正式執行位置。

### Q25：Claude 原本的專案都在 G 槽，要如何改成新架構？

**A：每個專案要先移到或 clone 到 C 槽，再讓 Claude 從 C 槽專案資料夾開工。**

調整原則：

1. 在 C 槽建立正式 project working tree。
2. 確認每個專案的 Git root 與 GitHub remote。
3. 補齊 `PROJECT.md`、`HANDOFF.md`、`AGENTS.md`、`CLAUDE.md`。
4. G 槽僅保留歷史或知識資料，不再執行。
5. 移除舊 `project-kickoff`，統一使用 `project-startup`。
6. 每個專案完成一次收工，建立可驗證的 GitHub 交棒點。

目前正式專案已依此方向調整；舊資料應保留觀察期，不要在尚未確認前直接刪除。

### Q26：使用工作列上的 Claude App，可以直接輸入 `cd C:\...\<專案名稱>` 嗎？

**A：一般 Claude Desktop 對話中的 `cd`，不能可靠地改變 Agent 的實際工作目錄。**

正確做法是：

- 在 Claude Code 或 Cowork 建立工作階段時，選擇 C 槽的正式專案資料夾。
- 確認畫面顯示的 folder 是正確路徑。
- 再要求執行「專案名稱 開工」。

Claude Desktop 也可透過 `claude://code/new?folder=...` deep link 開啟指定資料夾，但仍會要求使用者確認 folder。

## 八、架構版本與公開指南

### Q27：`agent-sync-v1.1.0` 是什麼？

**A：它是這套跨電腦、跨 Agent 同步架構的 release ID，不是軟體程式名稱，也不是 Claude 或 Codex 的模型版本。**

它代表一組已經一起測試、一起發布的內容：

- 四個 Skills
- 同步與健檢腳本
- `core_rule.md` 對應 hash
- Agent adapters
- Windows 排程規則
- 架構 manifest

目前 manifest：

```text
C:\Users\user\Documents\Codex\2026Claude\000_Agent\sync\architecture-manifest.json
```

來源 repo：

```text
https://github.com/scotthcliu-jpg/my-agent-2026.git
```

### Q28：什麼時候會「執行」`agent-sync-v1.1.0`？

**A：它本身不是一個按鈕或單一程式，因此不會被直接執行。**

實際上是下列流程讀取並驗證它：

- `project-init-sync` 建立新專案時
- `project-startup` 開工時
- `project-wrapup` 收工時
- `sync-health` 健檢時
- `Claude-SyncHealth-Weekly` 每週排程時

換句話說，`agent-sync-v1.1.0` 是被各流程共同遵守與驗證的「架構版本標記」。

### Q29：`agent-sync-v1.1.0` 與《跨電腦、跨 AI Agent 共生架構完整指南》有何不同？

**A：一個是已部署的機器規則，一個是給人看的操作說明。**

| 比較 | `agent-sync-v1.1.0` | 完整指南 |
|---|---|---|
| 定位 | 已部署架構版本 | 人類可讀的設計與安裝手冊 |
| 主要對象 | Skills、腳本、Agent、稽核工具 | 使用者、Migration Owner、其他建置者 |
| 是否會被檢查 | 會，以 manifest、Git commit、tag、hash 驗證 | 不會自動執行 |
| 存放位置 | `my-agent-2026` repo | 公開 `20260722-x-Computer-Agent-symbiosis` repo |
| 主要功能 | 真正阻擋分岔 | 解釋如何建立與操作這套架構 |

關係是：

```text
公開指南（設計與操作說明）
        ↓
Migration Owner 實作、測試
        ↓
my-agent-2026 commit + tag
        ↓
形成 agent-sync-v1.1.0
        ↓
各 Agent 透過四個 Skills 執行與驗證
```

### Q30：為什麼架構只能由單一 Migration Owner 實作一次？

**A：因為若每個 Agent 都各自修改同一套 Skills 與規則，就會出現多套「自認為正確」的架構。**

正確方式是：

1. 指定一位 Migration Owner。
2. 只在一個 branch 完成修改與測試。
3. commit、push、建立 release tag。
4. 其他 Agent 只取得同一個 Git commit。
5. 各 Agent 只套用自己的薄型設定，不另改核心規則。
6. 執行唯讀 `sync-health`，回報相同版本、hash 與路徑。

架構升版時也遵守同一原則，不讓多個 Agent 同時各改一套。

## 九、ChatGPT 畫面上的「新增至任務」

### Q31：ChatGPT 回覆上方的「新增至任務」要如何處理？

**A：它只是把該回覆另建成待追蹤任務的介面功能，不是同步架構的一部分。**

- 想把建議留成後續待辦：可以點「新增至任務」。
- 已經要由目前 Agent 直接執行：不一定要點。
- 點了也不代表檔案已修改、GitHub 已 push 或排程已建立。

真正是否完成，仍要看實際檔案、Git commit、remote HEAD 與驗證結果。

## 十、最終日常 SOP

### Q32：日後最簡單、最安全的操作方式是什麼？

**A：記住「新專案初始化、舊專案先開工、結束一定收工、每週再健檢」。**

#### 新專案

```text
project-init-sync
→ 在 C 槽建立正式 workspace
→ 建立 GitHub remote 與標準檔案
→ 第一次 commit + push
```

#### 每次開始工作

```text
選擇 C 槽正式專案
→ project-startup
→ 確認 handoff_ready: yes
→ 確認 remote、branch、HEAD、規則與 Skills
→ 通過後才修改
```

#### 每次結束工作

```text
完成修改與測試
→ project-wrapup
→ 更新 PROJECT.md 與 HANDOFF.md
→ commit + push
→ 驗證 local HEAD = GitHub remote HEAD
→ 驗證 HANDOFF hash
→ 寫入 Obsidian
```

#### 每週

```text
Claude-SyncHealth-Weekly
→ 執行完整唯讀 sync-health
→ PASS 才代表整體架構目前一致
```

## 最後判斷

這套架構不是讓所有儲存位置都存同一份完整專案，而是讓每一層各負責一件事：

- **C 槽 NTFS：工作**
- **Git/GitHub：定版與交棒**
- **Google Drive：全域規則發布與知識同步**
- **Obsidian：理解、學習與追蹤**

只要所有 Agent 都遵守「單一實作者、先開工、後收工、驗證 remote HEAD、失敗就阻擋」，就能把跨電腦與跨 Agent 的資料分岔風險降到可管理程度。
